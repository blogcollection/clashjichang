# Clash节点测速方法与指标解读：延迟RTT、真实带宽与单线程吞吐量测试

在选择和使用代理节点时，“测速”是用户最常用的评估手段。然而，许多人将客户端列表里的几毫秒延迟直接等同于“网速极快”，或者频繁进行大流量测速导致套餐过早耗尽。本文系统阐述 Clash 节点的科学测速方法、核心指标差异以及避坑防范。

---

## 一、指标辨析：延迟 (RTT) 与 带宽 (Throughput)

必须明确两个截然不同的物理概念：

1. **往返时延 (Round-Trip Time / RTT)**：
   - 数据包从本地发出，经过中转与落地服务器，返回确认包所需的时间，单位为毫秒 (ms)。
   - **影响体验**：网页点击响应灵敏度、外服游戏键盘指令同步。
   - 深入原理请阅读[Clash节点延迟怎么看：RTT与实际网速区别](/posts/how-to-read-clash-node-latency/)。
2. **带宽吞吐量 (Bandwidth / Throughput)**：
   - 单位时间内链路所能稳定传输的数据总量，单位通常为 Mbps 或 MB/s。
   - **影响体验**：4K/8K 视频播放是否缓冲、大文件下载耗时。
3. **丢包率 (Packet Loss)**：
   - 丢包率是性能杀手。即使延迟只有 40ms，如果公网出现 5% 的丢包，TCP 拥塞控制算法会迫使传输窗口急剧萎缩，网速断崖式下跌。

---

## 二、客户端内置测速的局限性

在 Clash Verge 或 CMFA 等客户端中，点击雷电图标所展示的毫秒数：

- **其测试原理**：向指定的测速 URL（如 Google 204 或 Cloudflare CDN）发送一次轻量的 HTTP HEAD/GET 握手请求。
- **局限性**：这仅仅反映了连接建立的往返耗时，**完全不代表该节点的真实下载带宽**。一个限制在 1Mbps 的超慢节点，完全可以跑出 35ms 的漂亮延迟。

---

## 三、真实带宽测试的科学实操

若需评估节点的真实承载能力，推荐以下方法：

### 1. Fast.com 测速 (针对 Netflix 节点)
- Fast.com 由 Netflix 官方提供，其服务器部署在 Netflix 的 Open Connect CDN 架构中。
- 在开启代理的状态下访问 Fast.com，可精准测试该节点访问海外主流流媒体时的真实下行带宽。

### 2. Speedtest.net 测速
- 访问 Speedtest 官网或客户端。
- **关键技巧**：测速服务器不要选择国内节点，应手动指定节点落地城市（如选东京节点测速时，测速服务器指定东京的 Vodafone 或 IPA）。这样测出的才是节点落地的真实出口能力。

### 3. YouTube 详细统计信息 (Stats for Nerds)
- 打开 YouTube，播放一段 4K 60FPS 或 8K 试机片。
- 在视频画面右键，点击 **“详细统计信息” (Stats for Nerds)**。
- 观察 **Connection Speed**（连接速度）：
  - 稳定在 `50,000 Kbps` 以上：可流畅观看 4K 视频。
  - 达到 `150,000 Kbps` 以上：节点带宽非常充裕。
  - 观察 **Buffer Health**（缓冲区健康度）：维持在 20 秒以上说明不会出现卡顿缓冲。

## 四、测速的巨大陷阱：高倍率流量黑洞

这是新手极易踩中的大坑：

1. 一次标准的千兆带宽 Speedtest 测速，上下行数据量轻松超过 **1.5GB - 2.5GB**。
2. 许多机场为了平衡专线成本，会对高速线路设置 **2x 至 5x 甚至更高倍率**（详见[什么是机场节点倍率](/posts/what-is-node-multiplier/)）。
3. 如果你在一个 5x 倍率节点上连续跑了 3 次测速，可能会被瞬间扣除超过 **30GB 套餐流量**！
4. **建议**：测速浅尝辄止，切忌在日常高倍率专线上频繁跑全量测速。
